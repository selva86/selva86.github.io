Partial pooling and the shrinkage it buys

Today let's understand partial pooling: a way to estimate several related groups from one shared dataset, so that every group borrows a little strength from all the others.

A retail chain piloted a new onboarding course for its newly hired sales associates in 8 of its branches. In each branch, it tracked how much an associate's monthly sales rose after taking the course, in dollars. The branches range from 3 associates in the smallest to 70 in the largest, 181 associates in total, and the raw average lift per branch ranges from \$13.3 to \$47.3.

Here is every branch's raw average lift plotted against how many associates it has.

Notice the branches with the fewest associates sit furthest from the pack, one of them the highest point on the whole chart, another near the lowest. The branches with the most associates sit much closer together. That pattern, small branches swinging wide and large branches settling down, is exactly what this lesson explains, and what to do about it.

Two easy answers and what each one costs you

Before getting to partial pooling, it helps to see the two simpler answers that sit on either side of it, and what each one costs you.

The first is called no pooling. It trusts each branch's own average completely, no matter how few associates it rests on. The branch with only 3 associates reported an average lift of \$47.3, and no pooling takes that \$47.3 as the branch's true effect, exactly as reported.

The second is called complete pooling. It throws away the branch labels altogether and pools every one of the 181 associates into one number: a single headcount-weighted average lift, applied to every branch alike. That discards any real difference between branches, treating the smallest branch and the largest branch as if they were identical.

Compute both.

RInteractive R
# Set up the 8 branches' data, then compare two easy ways to estimate each branch's lift. set.seed(42) n_i <- c(3, 5, 8, 12, 18, 25, 40, 70) true_i <- round(rnorm(8, 20, 8), 1) lift <- round(rep(true_i, n_i) + rnorm(sum(n_i), 0, 15), 1) branch <- factor(rep(1:8, n_i)) branches <- data.frame(branch = branch, lift = lift) means <- tapply(branches$lift, branches$branch, mean) grand_mean <- weighted.mean(means, n_i) round(means, 1) round(grand_mean, 2)

  

  





#>    1    2    3    4    5    6    7    8 
#> 47.3 18.9 13.3 24.6 21.1 20.8 32.4 17.2 
#> [1] 22.32



tapply() splits branches$lift by branch and applies mean() inside each group, so means holds each branch's own raw average. weighted.mean() then folds all 8 branch means back into one number, weighted by each branch's headcount n_i, the same number you would get by averaging all 181 associates directly: \$22.32.



So there are the two easy answers, side by side. No pooling says branch 1's true effect is \$47.3. Complete pooling says every branch's true effect, including branch 1's, is \$22.32.



Branch 1 only has 3 associates behind its number, so which of those two answers would you actually bet on? Neither one, fully, and closing that gap is exactly what partial pooling is for.







A prior whose width is estimated from the data



Partial pooling adds exactly one assumption on top of what you just saw. Instead of letting each branch's true effect be its own free-floating number, it treats every branch's true effect as one draw from a shared normal distribution, centred at the grand mean, with some spread you estimate from this exact data.



\[ \text{true effect}_i \sim \mathcal{N}(\text{grand mean}, \ \tau^2) \]



Think about what that spread, written \(\tau\) and read "tau", actually controls. If \(\tau\) were 0, every branch's true effect would be forced to equal the grand mean exactly. If \(\tau\) were enormous, each branch's true effect could sit almost anywhere, and the assumption would barely constrain anything. The real answer sits somewhere in between, and it can be estimated directly from the 8 branch means you already computed.



Before estimating \(\tau\), you need to pull apart two different kinds of noise. The first is ordinary sampling noise: even if two branches genuinely had the same true effect, their raw means would still differ a little, just because different associates happened to be sampled into each one. The second is real between-branch variation: some branches genuinely deliver more lift than others. \(\tau\) is meant to measure only the second kind, so the first kind has to be subtracted back out.




  

    
RInteractive R

    
# Pool the within-branch noise, get each branch's standard error, and estimate tau^2.
sigma_pooled <- sqrt(sum((branches$lift - rep(means, n_i))^2) / (sum(n_i) - 8))
se_i <- sigma_pooled / sqrt(n_i)
var_of_means <- var(means)
avg_sampling_var <- mean(se_i^2)
tau_hat2 <- var_of_means - avg_sampling_var

round(sigma_pooled, 2)
round(se_i, 2)
round(tau_hat2, 2)

    

      
      
    

    

  

  





#> [1] 14.63
#> [1] 8.45 6.54 5.17 4.22 3.45 2.93 2.31 1.75
#> [1] 93.34



sigma_pooled, 14.63, is the within-branch noise, pooled across all 8 branches into one shared number: how much a single associate's lift tends to vary around their own branch's true effect. Dividing it by the square root of each branch's headcount gives se_i, each branch's own standard error.



Branch 1, with only 3 associates, has a standard error of 8.45. Branch 8, with 70 associates, has a standard error of only 1.75. Fewer associates means a noisier raw mean, and the standard error is exactly how noisy.



var_of_means is the variance of the 8 raw branch means, and it mixes together the real between-branch variation you want with the ordinary sampling noise you do not. Subtracting the average squared standard error, avg_sampling_var, strips that sampling noise back out, leaving tau_hat2, 93.34, as the estimate of \(\tau^2\): how much the branches genuinely differ, once sampling noise has been accounted for. That is the one new ingredient partial pooling needed, and it came straight out of the data, not out of a guess.







The partial pooling formula: one weighted average



This is the heart of the whole lesson, so let's go slowly.



Partial pooling estimates each branch's effect as a weighted average of two things: that branch's own mean, and the grand mean. The weight is what makes it work: it is set by how much you can trust that one branch's own mean, compared to how much branches genuinely differ from each other.



\[ w_i = \frac{\hat\tau^2}{\hat\tau^2 + \text{se}_i^2} \]



Read it slowly. \(\hat\tau^2\), 93.34, is the same number for every branch: how much branches truly differ. \(\text{se}_i^2\) is that one branch's own squared standard error: how noisy its own mean is.



When a branch's standard error is small, because it has a lot of associates, \(\text{se}_i^2\) barely dents the denominator, so the weight sits close to 1. When a branch's standard error is large, because it has few associates, \(\text{se}_i^2\) can swamp \(\hat\tau^2\) in the denominator, pulling the weight down toward 0.



Once you have the weight, the partial-pooled estimate is just one more weighted average:



\[ \hat\theta_i = w_i \times \bar{y}_i + (1 - w_i) \times \bar{y} \]



where \(\bar{y}_i\) is that branch's own mean and \(\bar{y}\) is the grand mean. A weight near 1 leaves the estimate close to the branch's own mean. A weight near 0 pulls the estimate almost all the way to the grand mean.



Compute it for all 8 branches.




  

    
RInteractive R

    
# Blend each branch's own mean with the grand mean, weighted by tau_hat2 vs its own squared standard error.
weights <- tau_hat2 / (tau_hat2 + se_i^2)
partial <- weights * means + (1 - weights) * grand_mean

round(weights, 3)
estimates <- data.frame(no_pooling = round(means, 1),
                         complete_pooling = round(grand_mean, 1),
                         partial_pooling = round(partial, 1))
estimates

    

      
      
    

    

  

  





#> [1] 0.567 0.686 0.777 0.840 0.887 0.916 0.946 0.968
#>   no_pooling complete_pooling partial_pooling
#> 1       47.3             22.3            36.5
#> 2       18.9             22.3            19.9
#> 3       13.3             22.3            15.3
#> 4       24.6             22.3            24.3
#> 5       21.1             22.3            21.3
#> 6       20.8             22.3            21.0
#> 7       32.4             22.3            31.8
#> 8       17.2             22.3            17.4



Now look at the two extremes. Branch 1 has only 3 associates, so its weight is just 0.567, and its estimate moves from its raw \$47.3 nearly halfway to the grand mean, landing at \$36.5. Branch 8 has 70 associates, so its weight is 0.968, and its estimate barely moves, from \$17.2 to only \$17.4.



The branch with the least evidence moves the most. The branch with the most evidence barely moves at all.



That difference in movement is the shrinkage this lesson is named for. Every branch's estimate shrinks toward the grand mean, by exactly as much as its own evidence is weak, and not one bit more.







Watching the same pull happen on a different dataset



The branch numbers above came from one particular hand calculation. To see that the same mechanism is general enough to trust, here is a second dataset entirely, built into a widget you can drag yourself.



This widget's built-in data is 8 clinics instead of 8 branches, with sizes from 2 patients to 40 and a grand mean of 50. A slider moves between no pooling and complete pooling, with partial pooling in between. Drag it and watch each clinic's dot move.




At its default setting, clinic E, which has only 2 patients, gets pulled 12.8 toward the grand mean. Clinic D, which has 40 patients, barely moves at all, only 0.2. Drag the slider all the way to one end and every clinic sits exactly on its own raw mean, no pooling. Drag it all the way to the other end and every clinic collapses onto the one grand mean, complete pooling.



Partial pooling, in the middle, is what you have been computing by hand all along, with clinic standing in for branch, patient count standing in for headcount, and the exact same weight formula running underneath.







Quick check: why size changes the pull









Exactly. The weight is tau_hat2 over tau_hat2 plus that branch's own squared standard error, so a branch with a large standard error drags its own weight down and gets pulled further toward the grand mean.
The weight is about precision, not importance: a small branch is not demoted, its own mean is simply noisier, and that squared standard error in the denominator is what pulls its weight down. There is no headcount cutoff, the weight shifts smoothly for every branch, and the grand mean itself, \$22.32, stayed fixed the whole time; only each branch's own estimate moved.









Checked against lme4, the familiar mixed model



Everything so far was computed by hand, one step at a time. It is worth checking that hand calculation against a tool built for exactly this job: lme4's lmer(), which fits what statisticians call a mixed-effects model, sometimes also called a hierarchical model, with one random effect per branch.




  

    
RInteractive R

    
# Fit the same shrinkage with lme4's mixed model and compare to the hand calculation.
library(lme4)
fit <- lmer(lift ~ 1 + (1 | branch), data = branches)

round(fixef(fit), 1)
VarCorr(fit)
round(coef(fit)$branch[, 1], 1)

    

      
      
    

    

  

  





#> (Intercept) 
#>        23.4 
#>  Groups   Name        Std.Dev.
#>  branch   (Intercept)  7.0711 
#>  Residual             14.6998 
#> [1] 33.2 21.0 16.9 24.3 21.6 21.2 31.5 17.6



lmer(lift ~ 1 + (1 | branch), data = branches) fits one shared intercept for every associate, plus a random intercept allowed to vary by branch. fixef() returns that shared intercept, \$23.4, close to the \$22.32 grand mean you found by hand. VarCorr() reports the between-branch standard deviation, 7.07, found by a different method, called REML, restricted maximum likelihood, rather than your hand calculation, yet it lands in the same neighbourhood as \(\hat\tau\). And coef(fit)$branch gives each branch's own shrunk estimate: 33.2, 21.0, 16.9, 24.3, 21.6, 21.2, 31.5, 17.6, close to your hand-computed 36.5, 19.9, 15.3, 24.3, 21.3, 21.0, 31.8, 17.4.



Two completely different routes, your weighted average by hand and lmer()'s REML, land close to the same answer. Partial pooling is not a one-off trick someone invented for this lesson. It is what a standard mixed-effects model does automatically, every time you add a random effect for a grouping variable.







The same weighted average, written for any belief



The weight formula from a moment ago is not special to branches or clinics. It is one case of a more general rule, sometimes called a precision-weighted average: whenever a prior belief is combined with new data, the two get blended in proportion to how precisely each one is known. This widget shows that rule directly.




Its "prior mean" and "prior confidence" sliders set a starting belief, drawn as a normal distribution. Its "data average" and "data points n" sliders set what the new evidence says, and how much of it there is. The posterior, the blend of the two, is the third curve.



The "data points n" slider plays the same role a branch's headcount played. Drag it from low toward high and the posterior slides away from the prior and settles close to the data, tightening as it goes: the identical low-n-pulled-hard, high-n-barely-moves pattern you already saw with clinic E and clinic D, and computed by hand for branch 1 and branch 8.







Measured against a truth only a simulation can supply



Here is something you were not told until now. This dataset was not collected from a real retail chain. It was simulated, with each branch's true effect fixed in advance before any noise was added. That means, uniquely for this example, the right answer is actually known, so every one of the three estimates above can be scored against it.




  

    
RInteractive R

    
# Score each method against the true branch effects only a simulation can reveal.
sse_no_pooling <- sum((means - true_i)^2)
sse_complete_pooling <- sum((grand_mean - true_i)^2)
sse_partial_pooling <- sum((partial - true_i)^2)

round(c(no_pooling = sse_no_pooling, complete_pooling = sse_complete_pooling, partial_pooling = sse_partial_pooling), 1)

    

      
      
    

    

  

  





#>       no_pooling complete_pooling  partial_pooling 
#>            380.9            245.7            118.2 



The scoring rule is the summed squared error: take each method's 8 estimates, subtract the 8 true effects, square each difference, and add the 8 squares up. No pooling scores 380.9. Complete pooling scores 245.7, better, because averaging away the noise helps more than it hurts here. Partial pooling scores 118.2, the lowest of the three, by a wide margin.



Partial pooling wins because it is the only one of the three that uses the right amount of each branch's own evidence. It borrows heavily from the grand mean exactly where a branch's own evidence is weak, and barely borrows at all where a branch's own evidence is strong.



No pooling trusts weak evidence completely. Complete pooling throws away strong evidence completely. Partial pooling is the only one of the three that reads how strong the evidence actually is before deciding how far to lean on it.







Closing check: reading all three estimates together



A ninth branch reports a mean far from every other branch, and it rests on a very small headcount. Which is the right way to read its three possible estimates?









Exactly right. A small headcount means a large standard error, which means a small weight, which pulls the partial-pooled estimate hard toward the grand mean, and that is also the method that scored lowest on summed squared error.
None of these three survive what you just computed. The raw mean scored worst of the three methods, 380.9 against the known truth, so trusting it blindly is backwards. Setting the branch's own number aside entirely is complete pooling, which also lost to partial pooling, 245.7 against 118.2. And nothing in this lesson supports throwing a branch out for having a small headcount: a small headcount only means its own mean deserves less weight, not zero weight, and not exclusion.

A standard error of 2.07 is small, because 50 associates is a sizeable headcount. The pattern holds exactly as it did for branch 8 a few steps back: plenty of evidence means the branch is left close to where it already was.

A free lunch paid for by a modelling assumption



No pooling over-trusts small, noisy branches, taking a raw mean built from 3 associates as the final word. Complete pooling denies that branches differ at all, handing branch 1 and branch 8 the exact same number regardless of what either one actually did. Partial pooling blends the two, with a weight learned from the data itself rather than chosen by hand.



That blend is sometimes called a free lunch, since it costs nothing extra to compute and it beat both simpler answers on this lesson's own scoreboard, 118.2 against 245.7 and 380.9. But a free lunch is never really free. It is paid for by one modelling assumption: that every branch's true effect is a draw from one shared distribution, centred at a common grand mean.



Whenever that assumption roughly holds, as it did here, partial pooling wins. The moment branches belong to genuinely different worlds, with no shared story connecting them, that assumption breaks, and the borrowing it buys stops making sense.
