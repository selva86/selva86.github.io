Spatial Data in R with sf: Shapefiles, CRS Transformation, and ggplot2 Maps

The sf (simple features) package is R's modern standard for working with spatial data — points, lines, and polygons stored alongside regular data frame columns. It lets you read shapefiles, transform coordinate systems, and build publication-quality maps with ggplot2, all inside a tidy data workflow.

Note
This tutorial uses the sf package, which depends on system libraries (GDAL, GEOS, PROJ). The interactive code blocks may not run in the browser. If that happens, copy the code into RStudio — every block includes expected output so you can follow along either way. Install sf locally with install.packages("sf").

What does spatial data look like inside an sf object?

Every spatial analysis starts with getting geographic data into R and proving it loaded correctly. The sf package makes this straightforward: one function reads the file, and the result is a regular data frame with a special geometry column attached. Let's load sf and read a bundled shapefile of North Carolina counties to see what a spatial data frame looks like.

library(sf) library(dplyr) library(ggplot2) nc <- st_read(system.file("shape/nc.shp", package = "sf"), quiet = TRUE) nc #> Simple feature collection with 100 features and 14 fields #> Geometry type: MULTIPOLYGON #> Dimension: XY #> Bounding box: xmin: -84.32385 ymin: 33.88199 xmax: -75.45698 ymax: 36.58965 #> Geodetic CRS: NAD27 #> First 10 features: #> AREA PERIMETER CNTY_ CNTY_ID NAME FIPS FIPSNO CRESS_ID BIR74 SID74 #> 1 0.114 1.442 1825 1825 Ashe 37009 37009 5 1091 1 #> 2 0.061 1.231 1827 1827 Alleghany 37005 37005 3 487 0 #> 3 0.143 1.630 1828 1828 Surry 37171 37171 86 3188 5 #> 4 0.070 2.968 1831 1831 Currituck 37053 37053 27 508 1 #> 5 0.153 2.206 1832 1832 Northampton 37131 37131 66 1421 9 #> ...


  


  






That output reveals everything important. The nc object is a data frame with 100 rows (one per county) and 14 attribute columns — plus a geometry column that holds the polygon coordinates for each county boundary. The header tells you the geometry type (MULTIPOLYGON), the bounding box covering all of North Carolina, and the coordinate reference system (NAD27).



Think of an sf object as a spreadsheet where each row has a hidden shape attached. You can filter, mutate, and summarise it with dplyr, and the geometry column travels along automatically.

Each feature's geometry is a list of coordinate pairs tracing the boundary. You rarely need to touch these directly — sf functions handle them for you — but it helps to know they're just numbers.

An sf object is a data frame with a geometry column. Every dplyr verb you already know — filter(), mutate(), group_by(), summarise() — works on sf objects. The geometry column is "sticky" and follows along automatically, so you never lose the spatial information.

How do you read shapefiles and other spatial formats with st_read()?



A shapefile is the most common spatial data format you'll encounter, but it's actually not a single file. It's a bundle of at least three files that must travel together: .shp (the geometries), .shx (a spatial index), and .dbf (the attribute table). Most shapefiles also include a .prj file that stores the coordinate reference system.



Warning
Shapefiles are multi-file: always keep .shp, .shx, and .dbf together. If you move or rename just the .shp file, st_read() will fail. Download and extract the entire ZIP archive, then point st_read() at the .shp file — it finds the companion files automatically.



The st_read() function handles shapefiles, GeoJSON, GeoPackage, KML, databases, and more. It auto-detects the format from the file extension.





  


    
nc2 <- st_read(system.file("shape/nc.shp", package = "sf"))

#> Dimension:     XY
#> Bounding box:  xmin: -84.32385 ymin: 33.88199 xmax: -75.45698 ymax: 36.58965

Without quiet = TRUE, st_read() prints a summary of what it loaded: the driver (ESRI Shapefile), the feature count, geometry type, and CRS. This is useful for quick sanity checks when loading unfamiliar data.

Sometimes your spatial data doesn't come in a shapefile. You might have a CSV with latitude and longitude columns, or a data frame from an API. The st_as_sf() function converts a regular data frame into an sf object by specifying which columns contain the coordinates.





  


    
cities <- data.frame(

  lon  = c(-78.6382, -80.8431, -77.9447),
  lat  = c(35.7796,  35.2271,  34.2257)
)

cities_sf <- st_as_sf(cities, coords = c("lon", "lat"), crs = 4326)

The coords argument names the longitude and latitude columns (in that order — x before y), and crs = 4326 assigns the WGS 84 coordinate reference system, which is the standard for GPS coordinates.

What is a coordinate reference system (CRS) and why does it matter?



The Earth is roughly spherical, but maps are flat. A coordinate reference system defines the rules for translating 3D positions on the globe to 2D numbers on a page. Get the CRS wrong, and your layers won't align, your distance calculations will be off, or your map will show Antarctica the size of Africa.



There are two families of CRS, and understanding the difference saves you from the most common spatial data headache.



A geographic CRS uses latitude and longitude — angles measured in degrees from the equator and the prime meridian. EPSG:4326 (WGS 84) is the most common geographic CRS. It's what GPS devices output. It's great for storing and exchanging data, but the units are degrees, not meters, so you can't directly measure distances or areas.



A projected CRS converts those angles onto a flat surface using a mathematical projection. The result uses meters or feet as units. EPSG:3857 (Web Mercator) is what Google Maps and most web mapping tools use. UTM zones provide high-accuracy local projections for smaller regions.






Figure 2: Geographic CRS uses degrees on a sphere; projected CRS uses flat-surface coordinates in meters.



Every projection distorts something — area, shape, distance, or direction. Mercator preserves shape but inflates areas near the poles. Equal-area projections preserve area but warp shapes. The right choice depends on your analysis goal.

Here's why the distinction matters in practice. Let's compare area calculations under geographic vs projected CRS.





  


    
nc_proj <- st_transform(nc, crs = 32617)

area_geo <- st_area(nc[1, ])
area_proj <- st_area(nc_proj[1, ])

cat("Geographic CRS area:", area_geo, "\n")
#> Geographic CRS area: 1137107793 [m^2]
cat("Projected CRS area:", area_proj, "\n")
#> Projected CRS area: 1137388604 [m^2]

#> Difference: 0.28 sq km


    


      

      

    


    


  


  






The difference is small for a single county, but it compounds across large regions. For serious area or distance calculations, always use a projected CRS.



Tip
Use EPSG:4326 for storage and exchange, a local projected CRS for distance and area calculations. For North Carolina, UTM zone 17N (EPSG:32617) is a good choice. For the entire US, Albers Equal Area (EPSG:5070) preserves area.

How do you transform between coordinate systems with st_transform()?



When your data arrives in one CRS but your analysis needs another, st_transform() does the heavy lifting. It mathematically reprojects every coordinate in your sf object from the source CRS to the target CRS. You specify the target using an EPSG code.



Let's transform nc from its original NAD27 (EPSG:4267) to Web Mercator (EPSG:3857) and see how the coordinates change.





  


    
nc_mercator <- st_transform(nc, crs = 3857)
nc_mercator
#> Simple feature collection with 100 features and 14 fields
#> Geometry type: MULTIPOLYGON
#> Dimension:     XY
#> Bounding box:  xmin: -9386879 ymin: 4012882 xmax: -8399749 ymax: 4382110
#> Projected CRS: WGS 84 / Pseudo-Mercator
#> First 10 features:
#>    AREA PERIMETER CNTY_ CNTY_ID        NAME  FIPS FIPSNO CRESS_ID BIR74 SID74
#> 1 0.114     1.442  1825    1825        Ashe 37009  37009        5  1091     1
#> ...


    


      

      

    


    


  


  






Notice the bounding box values jumped from small degree numbers (-84 to -75) to large meter values (-9.3 million to -8.4 million). The attribute columns haven't changed — only the coordinates were reprojected.



Warning
st_transform() changes coordinates; st_set_crs() only changes the label. If your data is in WGS 84 but has no CRS assigned, use st_set_crs() to tag it. If your data is in WGS 84 and you need meters, use st_transform() to actually reproject the coordinates. Confusing these two is a common and painful mistake.



Let's plot the original and the transformed version side by side to see the visual difference.





  


    
p1 <- ggplot(nc) +

  theme_minimal()

p2 <- ggplot(nc_mercator) +

p1
#> (Map of NC counties in NAD27 projection)


    


      

      

    


    


  


  






The shape looks nearly identical for a small region like North Carolina, but the axis tick labels tell the story — the first map shows degrees, the second shows meters. Over larger areas (like a world map), the Mercator projection would stretch features near the poles dramatically.

How do you plot spatial data with geom_sf() in ggplot2?



The geom_sf() function is where sf and ggplot2 meet. It auto-detects whether your sf object contains points, lines, or polygons and draws the appropriate shape. You build maps the same way you build any ggplot — with layers, aesthetics, and scales.



Let's start with a basic map of North Carolina counties.





  


    
ggplot(nc) +
  geom_sf() +
  theme_minimal()
#> (Basic outline map of 100 NC counties)


    


      

      

    


    


  


  






That's the simplest possible map: county boundaries drawn in black on a white background. With one line of code, you have a correctly projected, properly scaled map.



To make a choropleth — a map where regions are colored by a data variable — map a column to the fill aesthetic. Let's color counties by their area.





  


    
ggplot(nc) +
  geom_sf(aes(fill = AREA), color = "white", size = 0.2) +
  scale_fill_viridis_c(option = "plasma", name = "Area") +
  ggtitle("North Carolina Counties by Area") +
  theme_minimal()
#> (Choropleth map: counties colored from dark purple (small) to yellow (large))


    


      

      

    


    


  


  






The viridis color scale is colorblind-friendly and prints well in grayscale. The color = "white" argument draws thin white borders between counties so they're visually distinct.



You can also change the map projection on the fly using coord_sf() without touching the underlying data. This is useful for display purposes — the data stays in its original CRS, but ggplot2 renders it in the projection you specify.





  


    
ggplot(nc) +
  geom_sf(aes(fill = AREA), color = "white", size = 0.2) +
  scale_fill_viridis_c(option = "plasma", name = "Area") +
  coord_sf(crs = st_crs(3857)) +
  ggtitle("NC Counties — Web Mercator Display") +
  theme_minimal()
#> (Same choropleth, rendered in Web Mercator projection)


    


      

      

    


    


  


  






Tip
coord_sf() can reproject the display without changing the data. Use it when you want a different visual projection but don't need to recalculate coordinates. For area or distance calculations, use st_transform() on the data itself.

How do you add labels, annotations, and styling to sf maps?



A map without labels is just a pretty shape. The geom_sf_text() and geom_sf_label() functions add text at each feature's centroid — the geometric center of the polygon.



Let's add county names to a few large counties.





  


    
nc_large <- nc |> filter(AREA > 0.2)

ggplot(nc) +
  geom_sf(fill = "lightyellow", color = "grey60") +
  geom_sf_text(data = nc_large, aes(label = NAME), size = 2.5,
               color = "darkred", fontface = "bold") +
  ggtitle("North Carolina — Largest Counties Labeled") +
  theme_minimal()
#> (Map with bold red labels on the largest counties: Robeson, Sampson, etc.)


    


      

      

    


    


  


  






For labels that might overlap, set check_overlap = TRUE to silently drop colliding labels, or use the ggrepel package for smarter placement.



Now let's put together a polished, publication-ready map. A professional map combines a clean theme, a meaningful color scale, a clear title, and appropriate borders.





  


    
ggplot(nc) +
  geom_sf(aes(fill = SID74), color = "white", size = 0.3) +
  scale_fill_distiller(palette = "YlOrRd", direction = 1,
                       name = "SIDS Deaths\n(1974)") +
  geom_sf_text(data = nc |> filter(SID74 > 15),
               aes(label = NAME), size = 2, color = "grey20") +
  labs(title = "Sudden Infant Death Syndrome in North Carolina, 1974",
       subtitle = "County-level SIDS death counts",
       caption = "Data: nc.shp bundled with the sf package") +
  theme_void() +
  theme(
    plot.title = element_text(size = 14, face = "bold"),
    plot.subtitle = element_text(size = 10, color = "grey40"),
    legend.position = "right"
  )
#> (Publication-quality choropleth: warm yellow-to-red gradient,
#>  labels on high-SIDS counties, clean white background)


    


      

      

    


    


  


  






The combination of theme_void() (removes axes, gridlines, and background), a diverging color palette, and selective labeling creates a map that communicates its message without visual clutter.



Tip
Use check_overlap = TRUE or the ggrepel package to prevent label collisions. For maps with many features, label only the most important ones by filtering the data passed to geom_sf_text().

How do you build sf geometries from scratch?



Sometimes your data arrives as raw coordinates — a CSV of sensor locations, a list of study area boundaries, or generated grid cells. The sf package gives you building blocks to construct any geometry type from coordinates: st_point(), st_linestring(), st_polygon(), then st_sfc() to bundle them into a geometry column, and st_sf() to attach attributes.



Let's build one of each geometry type step by step.





  


    
pt <- st_point(c(-79.0, 35.8))
line <- st_linestring(matrix(c(-80, 35, -78, 36, -77, 35.5), ncol = 2, byrow = TRUE))
poly <- st_polygon(list(matrix(c(-80, 35, -78, 35, -78, 36, -80, 36, -80, 35),
                                ncol = 2, byrow = TRUE)))

cat("Point:", class(pt), "\n")
#> Point: XY POINT sfg
cat("Line:", class(line), "\n")
#> Line: XY LINESTRING sfg
cat("Polygon:", class(poly), "\n")
#> Polygon: XY POLYGON sfg


    


      

      

    


    


  


  






Each st_*() call creates a single geometry object (sfg — simple feature geometry). A point is a single coordinate pair. A linestring is a sequence of coordinate pairs. A polygon is a ring of coordinates where the first and last points are identical (closing the shape).



Now let's combine these into an sf data frame with attribute columns.





  


    
geom_collection <- st_sfc(pt, line, poly, crs = 4326)

my_features <- st_sf(
  name = c("Weather Station", "Highway Segment", "Study Area"),
  type = c("point", "line", "polygon"),
  geometry = geom_collection
)

my_features
#>               name    type                       geometry
#> 1  Weather Station   point             POINT (-79 35.8)
#> 2  Highway Segment    line LINESTRING (-80 35, -78 36,...
#> 3       Study Area polygon POLYGON ((-80 35, -78 35, ...

ggplot(my_features) +
  geom_sf(aes(color = type), size = 2) +
  ggtitle("Custom Geometries from Scratch") +
  theme_minimal()
#> (Map showing a point, a line, and a rectangle in NC area)


    


      

      

    


    


  


  






The workflow is always the same: create individual geometries → bundle into st_sfc() with a CRS → wrap in st_sf() with attribute columns. The result is a full sf object you can plot, transform, or combine with other spatial data.



Note
Always set the CRS when creating geometries from scratch. Use st_sfc(..., crs = 4326) for lon/lat coordinates. Without a CRS, sf won't know how to project your data or align it with other layers.

Putting It All Together



Here's a complete workflow that reads spatial data, inspects its structure, transforms the CRS, computes a derived metric, and produces a publication-quality choropleth map.





  


    
nc_final <- st_read(system.file("shape/nc.shp", package = "sf"), quiet = TRUE) |>
  st_transform(crs = 32617) |>
  mutate(
    sid_rate = SID74 / BIR74 * 1000,
    area_km2 = as.numeric(st_area(geometry)) / 1e6
  )

cat("CRS:", st_crs(nc_final)$Name, "\n")
#> CRS: WGS 84 / UTM zone 17N
cat("Counties:", nrow(nc_final), "\n")
#> Counties: 100
cat("Columns:", ncol(nc_final), "\n")
#> Columns: 17
cat("SID rate range:", round(min(nc_final$sid_rate), 1),
    "to", round(max(nc_final$sid_rate), 1), "per 1000 births\n")
#> SID rate range: 0 to 9.7 per 1000 births

final_map <- ggplot(nc_final) +
  geom_sf(aes(fill = sid_rate), color = "white", size = 0.2) +
  scale_fill_distiller(
    palette = "YlOrRd", direction = 1,
    name = "SIDS Deaths\nper 1,000 Births"
  ) +
  geom_sf_text(
    data = nc_final |> filter(sid_rate > 6),
    aes(label = NAME), size = 2, color = "grey20"
  ) +
  labs(
    title = "Sudden Infant Death Syndrome Rates in North Carolina (1974)",
    subtitle = "SIDS deaths per 1,000 live births by county | UTM Zone 17N projection",
    caption = "Source: nc.shp dataset bundled with the R sf package"
  ) +
  theme_void() +
  theme(
    plot.title = element_text(size = 13, face = "bold"),
    plot.subtitle = element_text(size = 9, color = "grey40"),
    plot.caption = element_text(size = 7, color = "grey60"),
    legend.position = "right"
  )

final_map
#> (Publication-quality choropleth: yellow-to-red gradient showing SIDS rates,
#>  labels on the highest-rate counties, clean void theme, UTM projection)

Key Insight
sf turns spatial data into tidy data. The geometry column makes spatial objects behave like regular data frames. Every dplyr verb, every ggplot2 layer, every tidyr reshape just works — and the geometry follows along.
