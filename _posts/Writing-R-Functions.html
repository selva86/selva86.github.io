Write Better R Functions: Arguments, Defaults, Scope & When to Vectorise

An R function is a named block of code created with function() that accepts inputs (arguments), performs operations, and returns a result — letting you reuse logic without repeating code.

If you've ever copy-pasted a block of code and changed one value, you need a function. Functions eliminate repetition, reduce bugs, and make your code readable. Every serious R script is built from functions.

This tutorial covers everything you need to write clean, robust R functions: syntax, arguments with defaults, return values, scope rules, error handling, and vectorization.

Every code block below is interactive. Click Run to execute, edit to experiment, and Reset to restore the original.

Your First Function

A function has three parts: a name, arguments (inputs), and a body (the code that runs).

R
# Define a function greet <- function(name) { paste("Hello,", name, "- welcome to R!") } # Call it greet("Alice") greet("Bob")

    

  





The function greet takes one argument (name), builds a greeting string with paste(), and returns it. You call the function by typing its name followed by parentheses with the argument.



The Structure



function_name <- function(arg1, arg2, ...) {
  # body: do something with the arguments
  # the last expression is returned automatically
}



The assignment operator <- gives the function a name. The function() keyword starts the definition. The body goes inside curly braces {}.



Arguments and Defaults



Functions can have multiple arguments, and you can give them default values.




  

    

      R
      

        
        
      

    

    
# Function with default arguments
calculate_bmi <- function(weight_kg, height_m, round_to = 1) {
  bmi <- weight_kg / height_m^2
  round(bmi, round_to)
}

# Use all defaults
calculate_bmi(70, 1.75)

# Override the default
calculate_bmi(70, 1.75, round_to = 3)

# Arguments can be passed by position or by name
calculate_bmi(height_m = 1.75, weight_kg = 70)

    

    

  





round_to = 1 means "if the caller doesn't specify round_to, use 1." Required arguments (no default) must always be provided. Optional arguments (with defaults) can be omitted.



Positional vs Named Arguments




  

    

      R
      

        
        
      

    

    
describe <- function(name, age, city = "Unknown") {
  cat(name, "is", age, "years old, from", city, "\n")
}

# Positional — order matters
describe("Alice", 29, "London")

# Named — order doesn't matter
describe(age = 29, city = "London", name = "Alice")

# Mixed — positional first, then named
describe("Alice", 29, city = "London")

    

    

  





Best practice: use positional arguments for the first 1-2 commonly used arguments. Use named arguments for everything else. This makes function calls readable.



The ... (Dots) Argument



The special ... argument lets your function accept any number of extra arguments and pass them to another function.




  

    

      R
      

        
        
      

    

    
# ... passes extra arguments to an inner function
my_mean <- function(x, ...) {
  cat("Computing mean of", length(x), "values\n")
  mean(x, ...)
}

data <- c(10, 20, NA, 40, 50)

# Without na.rm — returns NA
my_mean(data)

# With na.rm — passed through ... to mean()
my_mean(data, na.rm = TRUE)

    

    

  





The ... pattern is everywhere in R. Functions like paste(), cat(), and c() all use it to accept any number of inputs.



Return Values



A function returns the last evaluated expression. You can also use return() for explicit returns.




  

    

      R
      

        
        
      

    

    
# Implicit return — last expression is returned
add <- function(a, b) {
  a + b  # This is returned
}

# Explicit return — useful for early exit
safe_divide <- function(a, b) {
  if (b == 0) return(NA)  # Early exit
  a / b
}

cat("add(3, 4):", add(3, 4), "\n")
cat("safe_divide(10, 3):", safe_divide(10, 3), "\n")
cat("safe_divide(10, 0):", safe_divide(10, 0), "\n")

    

    

  





Use implicit return (no return()) for simple functions. Use explicit return() for early exits when a special condition is met. Both are valid R style.



Returning Multiple Values



R functions can only return one object. To return multiple values, pack them in a list.




  

    

      R
      

        
        
      

    

    
# Return multiple values as a named list
summary_stats <- function(x) {
  list(
    mean = mean(x),
    sd = sd(x),
    min = min(x),
    max = max(x),
    n = length(x)
  )
}

data <- c(23, 45, 12, 67, 34, 89, 56)
result <- summary_stats(data)

cat("Mean:", result$mean, "\n")
cat("SD:", round(result$sd, 2), "\n")
cat("Range:", result$min, "to", result$max, "\n")

    

    

  





This is exactly how built-in R functions like lm() and t.test() work — they return a list with named elements you extract with $.



Scope and Environments



Scope determines where a variable is visible. Variables created inside a function exist only inside that function.




  

    

      R
      

        
        
      

    

    
x <- 100  # Global variable

my_function <- function() {
  y <- 50   # Local variable — only exists inside this function
  cat("Inside function: x =", x, ", y =", y, "\n")
}

my_function()

# x is still accessible
cat("Outside: x =", x, "\n")

# y does NOT exist outside the function
cat("Does y exist outside?", exists("y"), "\n")

    

    

  





The function can read the global variable x, but the local variable y is invisible outside. This is called lexical scoping.



Modifying Global vs Local Variables




  

    

      R
      

        
        
      

    

    
counter <- 0

# <- creates a LOCAL copy, does NOT modify global
increment_wrong <- function() {
  counter <- counter + 1  # Creates local 'counter', doesn't change global
  cat("Inside:", counter, "\n")
}

increment_wrong()
cat("Global counter:", counter, "\n")  # Still 0!

# <<- modifies the global variable (use sparingly!)
increment_right <- function() {
  counter <<- counter + 1
  cat("Inside:", counter, "\n")
}

increment_right()
cat("Global counter:", counter, "\n")  # Now 1

    

    

  





The <<- operator modifies variables in the parent environment. Use it sparingly — it makes code harder to debug because the function has hidden side effects. Prefer returning values instead.



Functions Can Return Functions (Closures)




  

    

      R
      

        
        
      

    

    
# A function factory — returns a customized function
make_multiplier <- function(factor) {
  function(x) x * factor
}

double <- make_multiplier(2)
triple <- make_multiplier(3)

cat("double(5):", double(5), "\n")
cat("triple(5):", triple(5), "\n")
cat("make_multiplier(10)(7):", make_multiplier(10)(7), "\n")

    

    

  





The inner function "remembers" the factor from its parent. This pattern is called a closure. It's advanced, but useful for creating families of related functions.



Error Handling with stop() and warning()



Good functions validate their inputs and give clear error messages.




  

    

      R
      

        
        
      

    

    
# Robust function with input validation
calculate_bmi <- function(weight_kg, height_m) {
  # Validate inputs
  if (!is.numeric(weight_kg)) stop("weight_kg must be numeric")
  if (!is.numeric(height_m)) stop("height_m must be numeric")
  if (weight_kg <= 0) stop("weight_kg must be positive")
  if (height_m <= 0) stop("height_m must be positive")
  if (height_m > 3) warning("height_m > 3 — did you pass centimeters instead of meters?")

  round(weight_kg / height_m^2, 1)
}

# Normal use
cat("BMI:", calculate_bmi(70, 1.75), "\n")

# Triggers warning (not an error — still runs)
cat("BMI:", calculate_bmi(70, 175), "\n")

    

    

  





stop() halts execution and throws an error. warning() prints a warning but lets the function continue. Use stop() for invalid inputs that would give wrong results. Use warning() for suspicious inputs that might still be valid.



Using tryCatch for Graceful Error Handling




  

    

      R
      

        
        
      

    

    
# tryCatch lets you handle errors gracefully
safe_log <- function(x) {
  tryCatch(
    log(x),
    warning = function(w) {
      cat("Warning caught:", conditionMessage(w), "\n")
      NA
    },
    error = function(e) {
      cat("Error caught:", conditionMessage(e), "\n")
      NA
    }
  )
}

cat("log(10):", safe_log(10), "\n")
cat("log(-5):", safe_log(-5), "\n")
cat("log('a'):", safe_log("a"), "\n")

    

    

  





tryCatch() wraps risky code and catches errors or warnings. The handler functions receive the condition and can return a fallback value. This prevents your entire script from crashing due to one bad input.



Writing Vectorized Functions



R works best with vectors. A well-designed function should work on single values and vectors alike.




  

    

      R
      

        
        
      

    

    
# This function is naturally vectorized
celsius_to_fahrenheit <- function(celsius) {
  celsius * 9/5 + 32
}

# Works on a single value
celsius_to_fahrenheit(0)

# Works on a vector — no loop needed
temps <- c(0, 20, 37, 100)
celsius_to_fahrenheit(temps)

    

    

  





Functions built from vectorized operations (+, *, /, paste(), ifelse()) are automatically vectorized. No extra work needed.



Using Vectorize() for Non-Vectorized Functions




  

    

      R
      

        
        
      

    

    
# This function uses if/else — NOT vectorized
classify_temp <- function(temp) {
  if (temp < 0) "freezing"
  else if (temp < 10) "cold"
  else if (temp < 25) "mild"
  else "hot"
}

# Works on one value
classify_temp(15)

# Fails on a vector:
# classify_temp(c(15, -5, 30))  # Error!

# Fix: use Vectorize()
classify_temp_v <- Vectorize(classify_temp)
classify_temp_v(c(-5, 3, 15, 30))

    

    

  





Vectorize() wraps your function so it loops over each element internally. It's convenient, but not faster than a real vectorized implementation. For performance-critical code, rewrite the function using ifelse() or dplyr::case_when() instead.



Practical Pattern: Building a Data Processing Pipeline



Here's how functions work in a real data analysis workflow. Each function does one thing well.




  

    

      R
      

        
        
      

    

    
# Step 1: Clean data
clean_scores <- function(scores) {
  scores <- scores[!is.na(scores)]   # Remove NAs
  scores <- scores[scores >= 0 & scores <= 100]  # Remove invalid
  scores
}

# Step 2: Compute stats
compute_stats <- function(scores) {
  list(
    mean = round(mean(scores), 1),
    median = median(scores),
    pass_rate = round(100 * mean(scores >= 60), 1)
  )
}

# Step 3: Format report
format_report <- function(stats, label = "Class") {
  cat("--- ", label, " Report ---\n")
  cat("Mean score:", stats$mean, "\n")
  cat("Median score:", stats$median, "\n")
  cat("Pass rate:", stats$pass_rate, "%\n")
}

# Pipeline: chain them together
raw <- c(88, NA, 45, 92, -5, 67, 78, 200, NA, 55)
cleaned <- clean_scores(raw)
stats <- compute_stats(cleaned)
format_report(stats, "Math 101")

    

    

  





Each function is small, testable, and reusable. You can swap out any step without touching the others. This is how professional R code is structured.



Documenting Your Functions



Always document what your function does, what it expects, and what it returns.




  

    

      R
      

        
        
      

    

    
# Well-documented function
# Description: Calculate weighted mean with optional trimming
# Arguments:
#   x      - numeric vector of values
#   w      - numeric vector of weights (same length as x)
#   trim   - fraction (0 to 0.5) of values to trim from each end
# Returns: single numeric value (the weighted, trimmed mean)
# Example: weighted_mean(c(10, 20, 30), c(1, 2, 1))

weighted_mean <- function(x, w, trim = 0) {
  if (length(x) != length(w)) stop("x and w must have same length")
  if (any(w < 0)) stop("weights must be non-negative")

  # Sort by value and apply trimming
  ord <- order(x)
  x <- x[ord]
  w <- w[ord]

  if (trim > 0) {
    n <- length(x)
    lo <- floor(n * trim) + 1
    hi <- n - floor(n * trim)
    x <- x[lo:hi]
    w <- w[lo:hi]
  }

  sum(x * w) / sum(w)
}

cat("Weighted mean:", weighted_mean(c(10, 20, 30), c(1, 2, 1)), "\n")
cat("With trimming:", weighted_mean(1:10, rep(1, 10), trim = 0.1), "\n")

    

    

  





A comment block above the function listing Description, Arguments, Returns, and Example follows the roxygen2 convention. If you later package your code, these comments convert directly to documentation.



Common Function Pitfalls




  

    

      R
      

        
        
      

    

    
# Pitfall 1: Mutable default arguments aren't a problem in R
# (Unlike Python, R evaluates defaults at call time)
add_to <- function(x, y = c(1, 2, 3)) {
  x + y
}
add_to(10)  # Works correctly every time

# Pitfall 2: Forgetting that R copies on modify
modify <- function(df) {
  df$new_col <- 1:nrow(df)  # Modifies local copy only
  df
}

original <- data.frame(a = c(10, 20, 30))
modified <- modify(original)
cat("Original has 'new_col'?", "new_col" %in% names(original), "\n")
cat("Modified has 'new_col'?", "new_col" %in% names(modified), "\n")

# Pitfall 3: Invisible returns
f <- function() invisible(42)
f()          # Nothing printed!
cat("Value:", f(), "\n")  # But the value is there

    

    

  





R uses copy-on-modify semantics. When you pass a data frame to a function and modify it, R works on a copy. The original stays unchanged. This is safe but can be confusing if you expect the function to modify the original.

FAQ



Should I use return() or just let R return the last expression?


Both are valid. The R community generally prefers implicit returns (no return()) for the final value. Use explicit return() only for early exits — when you want to bail out of a function before the end.



What happens if I forget to assign a function call to a variable?


The result is printed to the console and then discarded. If the function has side effects (like modifying a global variable or writing a file), those still happen. But the return value is lost.



Can I have a function with no arguments?


Yes. Define it as f <- function() { ... } and call it as f(). The parentheses are required even with no arguments. Without them, f prints the function definition instead of running it.



How do I make a function available across multiple R scripts?


Save your functions in a separate file (e.g., utils.R) and load it with source("utils.R") at the top of any script that needs them. For larger projects, consider building an R package.



What is the difference between <- and <<- inside a function?


<- creates or modifies a variable in the function's local environment. <<- searches up through parent environments and modifies the first match it finds (or creates one in the global environment). Avoid <<- unless you have a specific reason — it makes debugging harder.
