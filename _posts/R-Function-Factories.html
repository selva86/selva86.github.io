R Function Factories: How to Build Customisable Functions That Generate Functions

A function factory is a function that creates and returns another function. The returned function "remembers" its creation context through a closure — capturing the enclosing environment so that configuration values persist across calls.

This pattern sounds abstract until you see it in action. A factory lets you create families of related functions from a single template. Instead of writing square(), cube(), and fourth_power() separately, you write one power() factory and generate all three. This tutorial walks through 5 practical examples with interactive code.

Every code block below is interactive. Click Run to execute, edit to experiment, and Reset to restore the original.

The Basic Pattern

A function factory has three parts: it takes configuration as arguments, defines an inner function that uses that configuration, and returns the inner function.

R
# The factory power <- function(exponent) { function(x) x^exponent } # Create specialized functions square <- power(2) cube <- power(3) # Use them cat("5 squared:", square(5), "\n") cat("5 cubed:", cube(5), "\n") cat("3 squared:", square(3), "\n")

    

  





The factory power() creates specialized functions. Each one remembers its exponent value. This "remembering" is called a closure.



Why Use Function Factories?



Three practical reasons:



    

  1. Avoid repetition — Instead of writing similar functions over and over, create them from a template
    2. 

  2. Configuration — Create functions pre-loaded with settings (like a tax rate or threshold)
    3. 

  3. Composition — Build complex behavior from simple, configurable pieces

How Closures Work



When a function is created inside another function, it captures the enclosing environment — the set of variables that existed at the time of creation. Think of the inner function carrying a backpack full of those variables.




  

    

      R
      

        
        
      

    

    
make_greeter <- function(greeting) {
  function(name) {
    paste(greeting, name)
  }
}

hello <- make_greeter("Hello")
hi <- make_greeter("Hi")
howdy <- make_greeter("Howdy")

cat(hello("Alice"), "\n")
cat(hi("Bob"), "\n")
cat(howdy("Carol"), "\n")

    

    

  





You can inspect what a closure has captured:




  

    

      R
      

        
        
      

    

    
make_greeter <- function(greeting) {
  function(name) paste(greeting, name)
}

hello <- make_greeter("Hello")

# Peek inside the closure's backpack
cat("Captured variables:", ls(environment(hello)), "\n")
cat("Value of 'greeting':", get("greeting", environment(hello)), "\n")

    

    

  





Example 1: Power Function Factory



The classic example — create any power function from a single factory:




  

    

      R
      

        
        
      

    

    
power <- function(exponent) {
  force(exponent)
  function(x) x^exponent
}

square <- power(2)
cube <- power(3)
fourth <- power(4)
square_root <- power(0.5)

cat("5 squared:", square(5), "\n")
cat("5 cubed:", cube(5), "\n")
cat("5^4:", fourth(5), "\n")
cat("sqrt(25):", square_root(25), "\n")

# Works with vectors too
cat("\n1:5 squared:", square(1:5), "\n")

    

    

  





Notice the force(exponent) call. We'll explain why it's important in the pitfalls section below.



Example 2: Threshold Checker Factory



Create reusable threshold functions for data validation:




  

    

      R
      

        
        
      

    

    
above <- function(threshold) {
  force(threshold)
  function(x) x > threshold
}

is_adult <- above(17)
is_hot <- above(30)
is_expensive <- above(100)

ages <- c(12, 25, 17, 42, 8)
cat("Ages:", ages, "\n")
cat("Adults:", ages[is_adult(ages)], "\n\n")

temps <- c(28, 35, 22, 31, 29)
cat("Temps:", temps, "\n")
cat("Hot days:", sum(is_hot(temps)), "out of", length(temps), "\n\n")

prices <- c(50, 120, 99, 200, 75)
cat("Prices:", prices, "\n")
cat("Expensive items:", sum(is_expensive(prices)), "\n")

    

    

  





You can extend this pattern to create a between() factory:

between <- function(lo, hi) {
  force(lo); force(hi)
  function(x) x >= lo & x <= hi
}

is_working_age <- between(18, 65)
is_normal_temp <- between(36.1, 37.2)

ages <- c(12, 25, 70, 42, 8, 55)
cat("Working age:", ages[is_working_age(ages)], "\n")

temps <- c(36.5, 38.1, 36.8, 37.5, 36.0)
cat("Normal temps:", temps[is_normal_temp(temps)], "\n")

    

    

  





Example 3: Custom Formatter Factory



Build formatters for consistent output across your project:




  

    

      R
      

        
        
      

    

    
make_formatter <- function(prefix = "", suffix = "", digits = 2) {
  force(prefix); force(suffix); force(digits)
  function(x) {
    formatted <- formatC(round(x, digits), format = "f", digits = digits)
    paste0(prefix, formatted, suffix)
  }
}

format_usd <- make_formatter(prefix = "$", digits = 2)
format_pct <- make_formatter(suffix = "%", digits = 1)
format_temp <- make_formatter(suffix = "C", digits = 0)

cat(format_usd(1234.567), "\n")
cat(format_pct(85.67), "\n")
cat(format_temp(22.7), "\n")

# Works with vectors
prices <- c(9.99, 24.50, 149.95)
cat("\nFormatted prices:\n")
cat(paste(format_usd(prices), collapse = "\n"), "\n")

    

    

  





Example 4: ggplot2 Label Formatter Factory



ggplot2 scale functions accept formatter functions. Factories let you create custom label formatters that you can reuse across plots:




  

    

      R
      

        
        
      

    

    
label_currency <- function(prefix = "$", big.mark = ",") {
  force(prefix); force(big.mark)
  function(x) {
    paste0(prefix, formatC(x, format = "f", digits = 0, big.mark = big.mark))
  }
}

label_k <- function(suffix = "K") {
  force(suffix)
  function(x) {
    paste0(round(x / 1000, 1), suffix)
  }
}

# Test the formatters
fmt_usd <- label_currency()
fmt_euro <- label_currency(prefix = "\u20AC", big.mark = ".")
fmt_k <- label_k()

values <- c(500, 15000, 1500000)
cat("USD:  ", paste(sapply(values, fmt_usd), collapse = "  "), "\n")
cat("EUR:  ", paste(sapply(values, fmt_euro), collapse = "  "), "\n")
cat("Short:", paste(sapply(values, fmt_k), collapse = "  "), "\n")

    

    

  





In a ggplot2 call, you'd use these like: scale_y_continuous(labels = label_currency()).



Example 5: Memoization Factory



Memoization caches results so expensive computations only run once per unique input:




  

    

      R
      

        
        
      

    

    
memoize <- function(f) {
  cache <- list()
  function(...) {
    key <- paste(..., sep = "_")
    if (is.null(cache[[key]])) {
      cache[[key]] <<- f(...)
      cat("  [computed]\n")
    } else {
      cat("  [cached]\n")
    }
    cache[[key]]
  }
}

# A slow function (simulated)
slow_square <- function(x) {
  Sys.sleep(0.05)
  x^2
}

fast_square <- memoize(slow_square)

cat("First call with 5:")
fast_square(5)

cat("Second call with 5:")
fast_square(5)

cat("First call with 10:")
fast_square(10)

cat("Second call with 10:")
result <- fast_square(10)
cat("Result:", result, "\n")

    

    

  





The <<- operator is crucial here — it modifies the cache variable in the enclosing environment, not in the local scope. This is how the cache persists between calls.



Mutable State With <<-



Closures can maintain mutable state using <<-. Here's a counter:




  

    

      R
      

        
        
      

    

    
make_counter <- function(start = 0) {
  count <- start
  list(
    increment = function() {
      count <<- count + 1
      count
    },
    get = function() count,
    reset = function() {
      count <<- start
    }
  )
}

counter <- make_counter()
cat("Start:", counter$get(), "\n")

counter$increment()
counter$increment()
counter$increment()
cat("After 3 increments:", counter$get(), "\n")

counter$reset()
cat("After reset:", counter$get(), "\n")

    

    

  





Use this pattern sparingly. Mutable state makes code harder to reason about. But it's powerful when you need it — for caching, logging, or rate-limiting.



Common Pitfalls



Pitfall 1: The Lazy Evaluation Trap



R uses lazy evaluation. In a loop, all closures may capture the same variable (the loop counter), not the value it had when the closure was created:




  

    

      R
      

        
        
      

    

    
# BUG: all functions return the same result
funs_bad <- list()
for (i in 1:3) {
  funs_bad[[i]] <- function(x) x + i
}
# i is now 3, so ALL functions add 3
cat("Bad: ", funs_bad[[1]](10), funs_bad[[2]](10), funs_bad[[3]](10), "\n")

# FIX: use force() in a factory
make_adder <- function(n) {
  force(n)
  function(x) x + n
}

funs_good <- list()
for (i in 1:3) {
  funs_good[[i]] <- make_adder(i)
}
cat("Good:", funs_good[[1]](10), funs_good[[2]](10), funs_good[[3]](10), "\n")

    

    

  





force(n) evaluates the argument immediately instead of lazily. Always use force() in function factories when the argument is used inside the returned function.



Pitfall 2: Memory Leaks



Closures capture their enclosing environment. If that environment contains large objects you don't need, they stay in memory:




  

    

      R
      

        
        
      

    

    
# Wasteful — big_data stays in memory
bad_factory <- function() {
  big_data <- rnorm(1e5)
  result <- mean(big_data)
  function() result
}

# Better — big_data is garbage collected
good_factory <- function() {
  big_data <- rnorm(1e5)
  result <- mean(big_data)
  rm(big_data)
  function() result
}

fn_bad <- bad_factory()
fn_good <- good_factory()

cat("Bad closure env size:", length(ls(environment(fn_bad))), "objects\n")
cat("Good closure env size:", length(ls(environment(fn_good))), "objects\n")
cat("Same result:", fn_bad(), "vs", fn_good(), "\n")

make_scaler <- function(train_data) {
  lo <- min(train_data)
  hi <- max(train_data)
  function(x) (x - lo) / (hi - lo)
}

make_logger <- function(prefix = "LOG") {
  force(prefix)
  count <- 0
  function(msg) {
    count <<- count + 1
    cat(sprintf("[%s #%d] %s\n", prefix, count, msg))
  }
}

log <- make_logger("APP")
log("Server started")
log("User logged in")
log("Processing request")





FAQ



What's the difference between a closure and a regular function?



Every function in R is technically a closure — it has an enclosing environment. But we typically use "closure" to mean a function that uses variables from its enclosing environment that aren't passed as arguments.



Do function factories hurt performance?



No. The function creation is fast, and calling the returned function has the same overhead as calling any other function. The only cost is memory for the enclosing environment.



Can I see what a closure has captured?



Yes. Use environment(fn) to get the enclosing environment, ls(environment(fn)) to list captured variables, and get("var_name", environment(fn)) to inspect specific values.



When should I use a factory vs a function with extra parameters?



Use a factory when you want to configure once and call many times. Use a regular function with parameters when the configuration changes on every call. For example, format_usd(x) is cleaner than format_number(x, prefix = "$", digits = 2) when you always format as USD.



Are function factories common in R packages?



Yes. ggplot2's scale_* functions use factories for label formatters. purrr's possibly() and safely() are factories. The pattern appears throughout the tidyverse and base R.



Conclusion



A function factory creates functions. The returned function remembers its creation context through a closure. This pattern eliminates repetition, separates configuration from execution, and produces clean, composable code. Start with the power function example to build intuition, then apply the pattern to formatters, validators, and caching in your own projects. Remember to use force() to avoid the lazy evaluation trap, and rm() to prevent memory leaks from large captured objects. For related topics, see anonymous functions and purrr map().
