dplyr Joins in R: A Complete Guide (with Examples)

By Selva Prabhakaran·Updated Apr 2026·14 min read
Advertisement728 x 90 banner ad

Joins in dplyr let you combine two data frames using a common key. This guide covers inner_join, left_join, right_join, full_join, semi_join and anti_join with examples.

Table of Contents1. What are joins?2. inner_join()3. left_join()4. right_join() and full_join()5. semi_join() and anti_join()6. Conclusion

1. What are joins?

A join combines columns from two tables based on a matching key column. The dplyr package provides several join functions. The table below summarises them.

FunctionKeeps
inner_joinmatching rows only
left_joinall rows from x
right_joinall rows from y
full_joinall rows from both

2. inner_join()

Returns only the rows with a match in both data frames.

band_members %>% inner_join(band_instruments, by = "name") #> # A tibble: 2 x 3 #> name band plays #> John Beatles guitar #> Paul Beatles bass

3. left_join()

Keeps all rows from the left (x) data frame, filling unmatched rows with NA.

band_members %>% left_join(band_instruments, by = "name")
Advertisement300 x 250 in-content ad

4. right_join() and full_join()

right_join keeps all rows from y; full_join keeps all rows from both, filling with NA where there is no match.

band_members %>% full_join(band_instruments, by = "name")

5. semi_join() and anti_join()

semi_join keeps rows in x that have a match in y (filtering join). anti_join keeps rows in x with no match in y.

band_members %>% anti_join(band_instruments, by = "name")

6. Conclusion

You now know the six dplyr join functions. Practice them on your own data to get comfortable.

Joining data, and not silently corrupting it

Selva Prabhakaran14 min · runnable✓ written by a human

Most data does not arrive in one table. The skill that separates an analyst from a beginner is not knowing the six join verbs, it is knowing which one to reach for, and spotting the moment a join quietly doubles your rows or drops the customers you cared about.

The mental model

A join answers one question: for each row on the left, is there a matching row on the right? Everything else, all six verbs, is just a decision about what to do with the rows that match and the rows that do not.

left_join(customers, orders, by = "id")

Every customer survives (left side is sacred), order 4 is dropped because there is no customer 4, and Lin gets an NA because she has no order. Read the diagram until that is obvious; the rest of this lesson is consequences of it.

Choosing the join in one decision

Forget the six names. Ask two questions and the verb falls out:

left_join

Keep every row on the left, add matches where they exist. The default 90% of the time.

inner_join

Keep only rows that match on both sides. Use when unmatched rows are meaningless.

full_join

Keep everything from both sides. Use when you cannot lose any row.

semi_join

Filter the left to rows that have a match, without adding columns. A clean filter.

anti_join

Filter the left to rows with no match. The fastest way to find what is missing.

right_join

left_join with the tables swapped. Rare; usually clearer to flip the arguments.

See it run

joins.R
# a left join keeps every customer customers |> left_join(orders, by = "id")
#> # A tibble: 3 x 3 #> id name amount #> 1 1 Ada 40 #> 2 2 Lin NA <- kept, no order #> 3 3 Mo 12

Where joins quietly go wrong

This is the part the free guides skip, and the part that ships bugs to production.

⚠
The silent row explosion

If the key is not unique on the right, a join multiplies rows. Joining 1,000 customers to an orders table with duplicate ids can return 50,000 rows and a wrong total. Always check: does my key uniquely identify rows on the side I am joining to?

guard.R
# catch a many-to-many before it corrupts your numbers customers |> left_join(orders, by = "id", relationship = "one-to-many") # dplyr now errors loudly if the relationship is violated, instead of # silently returning too many rows.
⚙
Keys that do not match cleanly

An integer id on one side and a character "id" on the other will match nothing and warn. Trailing whitespace, case, and leading zeros are the usual culprits. Clean keys before you join, not after you debug.

Modern joins: join_by() and inequality joins

Since dplyr 1.1 you can join on conditions, not just equality, with join_by(). This is how you attach the price that was active on the date of the sale, a problem that used to need a messy workaround.

inequality.R
sales |> left_join(prices, join_by(product, between(date, start, end)))
★
How an expert actually does it

Before any join, run count(df, key) on both sides and eyeball the duplicates. Pick the verb from the decision above, set relationship = explicitly, and check the row count after. Three seconds of discipline that saves an afternoon of "why is revenue 4x too high."

Performance, when tables get big

dplyr joins are fine into the millions of rows. Past that, the same verbs exist in data.table and in duckdb via dbplyr, which join out of memory. The mental model does not change; only the engine does.

The five things to remember

  • A join asks "is there a match on the right?"; the verb decides what happens to the misses.
  • left_join is the default; reach for others deliberately.
  • A non-unique key on the right silently multiplies rows. Set relationship =.
  • Mismatched key types match nothing. Clean keys first.
  • join_by() unlocks inequality and rolling joins.
