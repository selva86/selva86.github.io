## C. Section outline

**Lead sentence (`<p class="lead">`):**
A closure is an R function that carries its defining environment with it — so the variables that existed when it was created stay alive every time you call it later. That single idea powers Shiny's `reactive()`, ggplot2's theme functions, and every function factory in the tidyverse.

**First H2 opening prose (≤80 words):**
> The fastest way to feel closures click is to build one. Below, a function called `make_counter()` returns *another* function. Each counter you create remembers its own running total, even though the original `make_counter()` call has long since finished. If you've ever wondered how Shiny's `reactive()` "remembers" its last value between button clicks, this short block is the whole trick in 6 lines.

#### H2 #5 — What are the three closure gotchas that bite everyone?
- **Gotcha 1 — Lazy evaluation.** Factory argument isn't evaluated until the returned function runs, so a loop that calls the factory can produce surprising results.
- **Code block 7:** the lazy-eval bug — `make_power()` called in a loop where all returned functions share the same (last) exponent.
- **Gotcha 2 — `force()` fixes it.**
- **Code block 8:** `force(n)` added to the factory.
- **Gotcha 3 — Closures hold their entire env.** Creating a closure inside a function that has a big object keeps that object alive. Mention `rm()` + `lobstr::obj_size()` briefly (but don't call lobstr in code since it may not be in WebR — just describe).
- Callout WARNING: always `force()` factory arguments used inside the returned function.
- Inline Try it: fix a given broken factory by adding `force()`.

- **Code block 9:** inspection toolkit applied to an earlier counter.
