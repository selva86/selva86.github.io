## C. Full Section Outline

### Lead paragraph

R6 inheritance lets a child class reuse and extend a parent's methods, private fields hide internal state from outside code, and active bindings (computed properties) run a function every time you read or write a field — giving you validation, caching, and derived values with simple `obj$field` syntax.

### First H2 opening plan (≤80 words)

"When two classes share logic — say a DataSource and a CsvSource — copying code between them breaks the moment you fix a bug in one but forget the other. Inheritance solves this: define shared behavior once in a parent, then let children specialize. Let's build a parent-child pair and see how super$ delegates back to the parent."

### Core Content Sections

#### H2 1: How does R6 inheritance work?
- Theory: `inherit` argument, child gets all parent public/private methods, single inheritance only
- Code block 1 (PAYOFF): Define Animal parent + Dog child, create dog, call inherited + overridden method, show output
- Code block 2: Show super$ to call parent's initialize inside child
- Callout: KEY INSIGHT — R6 is single inheritance; for composition, use fields holding other R6 objects
- Inline exercise: Create a Cat child that overrides speak() to say "Meow"

#### H2 2: How do you override and extend parent methods with super$?
- Theory: Method overriding, super$ delegation pattern, when to call super vs replace entirely
- Code block 3: Multi-level hierarchy (Shape → Rectangle → Square) with super$initialize chaining
- Code block 4: Adding new methods in child that use parent's private state
- Callout: TIP — Always call super$initialize() first in child constructors so parent state is ready before child uses it
- Inline exercise: Add an area() method to Square that uses width from parent

#### H2 3: What are private fields and methods in R6?
- Theory: Encapsulation, private$ access, why hide internals (refactoring safety)
- Code block 5: BankAccount with private balance, public deposit/withdraw that validate
- Code block 6: Show that external access to private$ fails with error
- Callout: WARNING — R6 subclasses CAN access parent's private methods (via super$), but NOT private fields directly
- Inline exercise: Add a private transaction_log list and a public get_history() method

#### H2 4: How do active bindings create computed properties?
- Theory: Active bindings = functions that look like fields, getter/setter pattern using missing(value)
- Code block 7: Circle class with private radius, active binding area that computes pi*r^2 on read
- Code block 8: Read-write active binding with validation (setting radius rejects negatives)
- Diagram: R6-Advanced-active-binding-flow.webp
- Callout: KEY INSIGHT — Active bindings let you add validation without changing how users interact with the object — obj$area still looks like a field
- Inline exercise: Add a circumference active binding to Circle

#### H2 5: How does finalize() clean up resources?
- Theory: finalize called during garbage collection, use for closing connections/files/temp dirs
- Code block 9: TempFile class with finalize that deletes the file, demonstrate with gc()
- Callout: NOTE — finalize() should be private — no reason for external code to call it
- Inline exercise: Add a print message to finalize confirming cleanup happened

#### H2 6: When should you use portable vs non-portable R6 classes?
- Theory: portable=TRUE (default) uses self$/private$, non-portable uses environment directly, cross-package considerations
- Code block 10: Show the difference in method body syntax
- Callout: TIP — Always use portable (default). Non-portable exists for historical reasons only.
- Inline exercise: Convert a non-portable class to portable
