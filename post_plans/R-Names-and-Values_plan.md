## C. Outline

**Lead sentence (<p class="lead">):**
> In R, names point to values — not the other way round. When you write `y <- x`, R does *not* copy the data. It only makes a new copy when you actually modify one of them. This rule — called **copy-on-modify** — is the reason R feels both safe and sometimes unexpectedly slow.

**First H2 opening prose (≤80 words):** For the question *"What does it mean for names to point to values in R?"* — "Most languages put the variable on the left of an arrow pointing to memory. R flips it. The name `x` is a label attached to a value sitting somewhere in memory, and two names can share the same label target. The `lobstr` package lets you peek at those memory addresses directly — here is what happens when you assign one vector to another."

### Core H2 sections (5)

**H2 #1 — What does it mean for names to point to values in R?**
- Mental model: names are labels, values live in RAM
- Code block 1 (payoff): `library(lobstr); x <- c(1,2,3); y <- x; obj_addr(x); obj_addr(y)` — same address
- Callout: [KEY INSIGHT] "The object doesn't own the name; the name owns the object."
- Inline exercise: `ex_a <- 1:5; ex_b <- ex_a` — check same address

**H2 #2 — When does R actually copy your data?**
- Introduce `tracemem()` to see copies happen live
- Code block 2: `tracemem(y); y[1] <- 99` — shows "tracemem[OLD -> NEW]" trace
- Code block 3: `obj_addr(x)` unchanged, `obj_addr(y)` new; `untracemem(y)`
- Diagram: `R-Names-and-Values-copy-on-modify-flow.webp` (Figure 1)
- Callout: [NOTE] "Reassignment `y <- something` and modification `y[1] <- 99` both create new objects."
- Inline exercise: trace and modify a second variable

**H2 #3 — How are lists and data frames actually copied?**
- Lists are shallow copies — the container is copied, not the elements
- Code block 4: `lst <- list(a=1:3, b=4:6, c=7:9); ref(lst)` — show element addresses
- Code block 5: `lst2 <- lst; lst2$a <- 99; ref(lst); ref(lst2)` — only `$a` gets a new address
- Diagram: `R-Names-and-Values-shallow-copy.webp` (Figure 2)
- Callout: [TIP] "Data frames are lists of column vectors — so modifying one column only copies that column, not the whole frame."
- Inline exercise: modify one column of `mtcars` copy and check which columns share addresses

**H2 #4 — When does R modify in place instead?**
- The two exceptions: objects with a single reference, and environments
- Code block 6: `v <- c(10, 20, 30); tracemem(v); v[1] <- 99` — shows in-place optimisation (or copy, depending on refcount)
- Code block 7: environments are reference semantics: `e <- new.env(); e$x <- 1; f <- function(env) env$x <- 999; f(e); e$x` → 999
- Callout: [WARNING] "Functions in R are pass-by-value for vectors and lists, but environments break that rule. Mutating an environment from inside a function affects the caller."
- Inline exercise: pass an env to a function and mutate

**H2 #5 — How does this affect your code's speed and memory?**
- Code block 8: slow loop-based data frame growth vs vectorised assignment — show `obj_size` and rough timing
- Code block 9: `obj_size(lst)` vs `obj_size(lst, lst, lst)` — shared values cost nothing extra
- Callout: [KEY INSIGHT] "Every in-loop modification of a data frame triggers a fresh copy. One vectorised assignment replaces thousands of copies."
- Inline exercise: rewrite a small grow-in-loop to vectorised
