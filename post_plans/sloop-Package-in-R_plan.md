## Lead Sentence

R has four OOP systems (S3, S4, RC, R6), and from the outside an unfamiliar object rarely tells you which one it uses. The **sloop** package answers "what kind of object is this?" and "which method will run?" in a single line instead of three base-R calls stitched together.

## First H2 Opening Plan (≤80 words)

*Between the H1/lead and the first payoff code block:*

> Suppose a colleague hands you a fitted model and asks why `predict()` behaves oddly on it. Before you can debug, you need three facts: its class, its OOP system, and which `predict` method actually runs. Base R makes you chain `class()`, `isS4()`, `methods()` and `getAnywhere()` to get there. sloop answers all three questions with three function calls — short enough to type from memory.

### H2 1 — "What does sloop do that base R doesn't?"

- **Intent:** Motivate the whole package with a concrete "mystery object" scenario. Hit the payoff result early.
- **Payoff code block (Block 1):** Fit an `lm()`, then call `sloop::otype()`, `sloop::s3_dispatch(print(fit))`, show `#>` output. Single block, visible one-line answers.
- **Interpretation:** Three answers, one import. Readers recognise the pain (multi-step base-R equivalents) and the value (unified API).
- **NOTE callout:** sloop lives on CRAN. If the interactive runtime below doesn't include it, the `#>` output still shows what you'd see in local R — and the base-R alternatives in later sections all run in-browser.
- **Inline "Try it":** Swap `lm()` for `glm(am ~ wt, data = mtcars, family = binomial)` and call `otype()` + `s3_dispatch(print(...))`. Reveal shows expected output.

### H2 2 — "How does otype() identify an object's OOP system?"

- **Intent:** Teach the one-word answer otype returns and connect it to the four OOP systems.
- **Code block 2:** Call `otype()` on an integer, a data.frame, a factor, an lm fit, an S4 object. Expected `#>` output: `"base"`, `"S3"`, `"S3"`, `"S3"`, `"S4"`.
- **Code block 3 (base-R alternative):** Define `identify_oop(x)` using `isS4()`, `is.environment()`, and `attr(x, "class")`. Show it agrees with otype on the same inputs. This block is fully runnable in the interactive runtime.
- **TIP callout:** Prefer `otype()` over `class()` for the OOP question. `class()` tells you what the object *is* called; `otype()` tells you which dispatch engine processes it.
- **Inline "Try it":** Write a one-liner that returns the OOP system of `ex_f <- factor(c("a","b"))`. Expected: `"S3"`.

### H2 3 — "How does ftype() classify R functions?"

- **Intent:** Distinguish generics, methods, and regular/primitive functions.
- **Code block 4:** `ftype(print)`, `ftype(print.data.frame)`, `ftype(mean)`, `ftype(sum)`, `ftype(unclass)`. Expected `#>` output: `c("S3","generic")`, `c("S3","method")`, `c("S3","generic")`, `c("S3","generic","group")`, `"primitive"`.
- **Code block 5 (base-R alternative):** Write `is_generic_body(f)` that checks for `"UseMethod"` or `"standardGeneric"` in `deparse(body(f))`. Run on `mean`, `print`, `sum`, `nchar`.
- **Interpretation:** Explains the "group generic" label (from `Summary` group), why `unclass` is primitive, and when to trust the body-scan fallback.
- **Inline "Try it":** Use ftype (or the manual version) to classify `t.test`.

### H2 4 — "How does s3_dispatch() trace S3 method dispatch?"

- **Intent:** Make the `=>`, `->`, `*` symbols concrete. This is the package's killer feature.
- **Code block 6:** `s3_dispatch(print(mtcars))`, `s3_dispatch(print(factor(1:3)))`, `s3_dispatch(summary(lm(mpg ~ wt, data = mtcars)))`. Show the method-chain output with arrows.
- **KEY INSIGHT callout:** `=>` is the method R will *actually* run; `*` is a method that exists but was skipped; `->` is a method `NextMethod()` will call later. Readers who internalise these three symbols can debug any dispatch puzzle.
- **WARNING callout:** `s3_dispatch()` only traces S3. On an S4 object it returns nothing useful — use `selectMethod()` or `showMethods()` instead.
- **Code block 7 (base-R alternative):** Loop over `class(obj)` building `paste0(generic, ".", cls)` names and test each with `exists(..., mode = "function")`. Output mirrors the sloop arrows.
- **Inline "Try it":** Call `s3_dispatch(format(Sys.Date()))` and predict which method wins.

### H2 5 — "How do you list all methods for a generic or class?"

- **Intent:** Close the loop on discovery — once you know a generic or a class exists, how do you see everything attached to it?
- **Code block 8:** `s3_methods_generic("mean")` and `s3_methods_class("Date")`. Show the tibble-style output (generic, class, visible, source).
- **Code block 9 (base-R alternative):** `methods("mean")` and `methods(class = "Date")`. Same information, different format; explain when the tibble helps (filtering, piping).
- **TIP callout:** Reach for `s3_methods_class()` when you're shopping for a class to subclass — it shows you every operation the class already supports.
- **Inline "Try it":** List all methods for the `glm` class and count them.
