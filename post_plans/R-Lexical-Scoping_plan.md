## E. Section outline

### H2 #1 — What is lexical scoping in R?

- Opening prose (above)
- **Block 1 (payoff):** free variable lookup + call-time resolution

```r
x <- 10

f <- function() {
  # f never defines x — R walks outward to find it
  x + 1
}

f()
#> [1] 11

# Change x AFTER f was defined
x <- 99
f()
#> [1] 100
```

- Interpretation: R found `x` in the env where `f` was defined (global). Second call proves lookup happens at **call time**, not define time.
- Definition: lexical = based on where code is **written**.
- [KEY INSIGHT] callout: "Lexical" = Greek *lexis* (word). R decides where to look based on the textual location of the function, not the call site.
- Inline exercise: write a function `ex_times_k` that uses an outer `k` to multiply its argument; change `k` and re-run.

### H2 #2 — How does R walk environments to find a variable?

- Explain env chain: current function env → enclosing env (where function was defined) → its parent → … → global env → attached packages → base.
- Figure 1: `R-Lexical-Scoping-env-chain.webp` — Horizontal flowchart of the walk.
- **Block 2:** nested function — each level looks up a variable not defined locally

```r
outer <- function() {
  y <- 2
  inner <- function() {
    # z not here, not in outer — walk to global
    y + z
  }
  inner()
}

z <- 100
outer()
#> [1] 102
```

- Interpretation: `inner()` looks locally (no `z`), then in `outer()` (no `z`), then in global (found). `y` is found in `outer()`.
- **Block 3:** show `search()` and `environmentName(globalenv())`


### H2 #3 — What are the four rules of R lexical scoping?

- Advanced R (Wickham) structures scoping as four rules. Teach them here with a tight example per rule.
- Figure 3: `R-Lexical-Scoping-four-rules.webp` — mindmap. Placed right after the opening paragraph.
- Rule 1 — **Name masking**: local before outer.
- **Block 4:**

```r
x <- "global x"

g <- function() {
  x <- "local x"
  x
}

g()
#> [1] "local x"
x
#> [1] "global x"
```

- Interpretation: `g()` finds its own `x` first. Global `x` is untouched.

- Rule 2 — **Functions vs variables**: R can use the same name for a function and a variable; when you call `foo()`, R skips non-function bindings.
- **Block 5:**

```r
n <- function(x) x * 2

test <- function() {
  n <- 10         # a number called n
  n(5)            # still calls the function n
}

test()
#> [1] 10
```

- Interpretation: R walked past the local `n = 10` because the call-site expected a function. (This only applies in call context.)
- [WARNING] callout: "**Don't rely on this trick.** It works, but shadowing a function name with a variable of the same name is a reader-hostile pattern. Rename one of them."

- Rule 3 — **A fresh start**: every call creates a new environment.
- **Block 6:**

```r
f <- function() {
  if (!exists("count")) count <- 0
  count <- count + 1
  count
}

f()
#> [1] 1
f()
#> [1] 1
```

- Interpretation: Each call creates a new env; `count` starts over every time. (This is why you need closures or `<<-` to persist state.)

- Rule 4 — **Dynamic lookup**: lookup happens when you *call* the function, not when you define it.
- **Block 7:**

```r
y <- 10
h <- function() y * 2
h()
#> [1] 20

y <- 1000
h()
#> [1] 2000
```

- Interpretation: `h()` picks up whatever `y` is at call time. Convenient — but can bite when an outer variable changes unexpectedly.
- [TIP] callout: "**Use `codetools::findGlobals(h)` to list outer names your function depends on.** That's the fastest audit for 'what will break if I rename something upstream?'"
- Inline exercise: rewrite `f()` (Rule 3) to actually count across calls using `<<-`.

### H2 #4 — How do you handle name masking safely in R?

- Real pitfall: you load `dplyr` and suddenly `filter()` means a different thing (base R has `stats::filter()` too).
- **Block 8:** show `library(dplyr)` attaches functions on top of the search path; base `filter` is now masked.

```r
library(dplyr)
# The attach prints something like:
# The following objects are masked from 'package:stats':
#     filter, lag

# Call the dplyr version
mtcars |> filter(mpg > 25) |> nrow()
#> [1] 6

# Explicitly call the base version
stats::filter(c(1, 2, 3, 4, 5), rep(1, 2))
#> Time Series:
#> ...
```

- Interpretation: `::` pins the lookup to a specific package — bypasses the search path entirely.
- Figure 4: `R-Lexical-Scoping-masking-decision.webp` — small flowchart.
- [KEY INSIGHT] callout: "**`pkg::func()` is the only lookup that can never be masked.** Use it in production code, package code, and anywhere you can't see what else the user has loaded."
- Inline exercise: Given a script that breaks after someone loads `stats::filter`, fix the call so it always uses `dplyr::filter`.

### H2 #5 — How does lexical scoping enable closures in R?

- Intuition: A closure is a function *plus* the environment it was defined in. Because R uses lexical scoping, that environment sticks around as long as the function does — so the function can carry data with it.
- **Block 9:** counter factory

```r
make_counter <- function() {
  count <- 0
  function() {
    count <<- count + 1
    count
  }
}

counter1 <- make_counter()
counter2 <- make_counter()

counter1()
#> [1] 1
counter1()
#> [1] 2
counter2()
#> [1] 1
```

- Interpretation: Each call to `make_counter()` creates a fresh env. `counter1` and `counter2` each capture *their own* `count`. `<<-` assigns in the parent env (the closure), not global.
- [NOTE] callout: "**Closures back Shiny's reactive values and ggplot2's theme system.** Once you see the pattern here, those become a lot less mysterious."
- Inline exercise: build `ex_make_adder(n)` that returns a function which adds `n` to its input.

### H2 #6 — How does lexical scoping differ from dynamic scoping?

- Quick theory: **dynamic scoping** looks up names based on the *call site*, not the definition site. Perl, older Lisps, and R's `with()` / `subset()` simulate dynamic scoping via non-standard evaluation. R's default is lexical.
- **Block 10:** two views of the same code — lexical (R's default) vs simulated dynamic via `local()`/explicit env.

```r
a <- "outer a"

caller <- function() {
  a <- "caller a"
  callee()
}

callee <- function() a

# Lexical: callee's `a` resolves in the env where callee was defined
# (global), NOT in caller()
caller()
#> [1] "outer a"
```

- Interpretation: Under dynamic scoping, `callee()` would have seen `"caller a"`. Under R's lexical rule, it only sees the global `a`.
- [TIP] callout: "**Want to test a function in a fake environment?** Use `local({ ... })` or build an env with `new.env()` and `environment(f) <- e`. That's lexical scoping turned into a tool."
- Inline exercise: predict the output of a similar call-then-lookup block.

### H2 #8 — Complete Example: rate-limited function factory

End-to-end: build `rate_limit(f, max_calls)` that wraps any function so it errors out after `max_calls` calls. This uses all four rules:
- Closure captures state
- Fresh start gives each wrap its own counter
- Dynamic lookup reads `max_calls` from the enclosing env at call time
- Name masking: the wrapper uses `call_count` without colliding with the wrapped function's names

```r
rate_limit <- function(f, max_calls) {
  call_count <- 0
  function(...) {
    if (call_count >= max_calls) {
      stop("Rate limit of ", max_calls, " calls exceeded")
    }
    call_count <<- call_count + 1
    f(...)
  }
}

limited_print <- rate_limit(print, max_calls = 3)
limited_print("hello")
limited_print("world")
limited_print("foo")
# limited_print("bar")  # would error
```
