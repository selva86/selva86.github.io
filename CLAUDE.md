## Skills / Slash Commands

Three project skills automate the content pipeline. They are defined in `.claude/skills/`.

### `/write-post-interactive` — Write a Tutorial

**What it does:** Researches a topic, analyzes competitors, writes a complete interactive R tutorial as markdown.

**Input:** A topic string (e.g., `"Random Forest in R"`)

**Output:** A markdown file saved to `posts/<slug>.md`

**Process:**
1. Web search for top 5-8 competitors on the topic
2. Print competitor analysis table (strengths, weaknesses, gaps)
3. Craft SEO-optimized title (under 60 chars), slug, meta description (150-160 chars)
4. Plan a comprehensive outline that covers everything competitors cover + unique sections
5. Write the full tutorial with interactive `r` code blocks, exercises, FAQ, summary
6. Save to `posts/<slug>.md`

**Frontmatter produced:**
```yaml
---
title: "<SEO title>"
slug: "<Slug-With-Dashes>"
description: "<150-160 char meta description>"
keywords: "<comma-separated>"
mathjax: true/false
webr: true
date: "<YYYY-MM-DD>"
curriculum_id: "<id, e.g. 4.2.3>"
post_type: "<C, FR, EX, or PSEO>"
sidebar_section: "<e.g. Learn R — for C posts>"
sidebar_title: "<short title, e.g. R Closures — for C and EX posts>"
sidebar_order: "<position in section — for C and EX posts>"
auto_link_terms: "<pipe-separated terms>"
auto_link_case_sensitive: false
fr_parent: "<parent-slug.html — for FR, EX, and PSEO posts>"
---
```
See `_build/frontmatter-spec.md` for the full field reference.

### `/publish-post` — Build & Publish a Post

**What it does:** Takes a markdown post, converts to HTML, updates sidebar and curriculum, builds, commits, and pushes live.

**Input:** A slug or path (e.g., `R-Closures` or `posts/R-Closures.md`), optional `--dry-run`

**Output:** A live page at `https://r-statistics.co/<slug>.html`

**Process (9 steps):**

| Step | Action | Skipped in --dry-run? |
|------|--------|----------------------|
| 1 | Locate and validate the markdown file, extract frontmatter | No |
| 2 | Convert markdown to interactive HTML (R blocks → WebR containers) | No |
| 3 | Create `_posts/<slug>.html` with HTML frontmatter | No |
| 4 | Update `curriculum-status.json` (set status=published, slug, url, date) | Yes |
| 5 | Update `sidebar.json` — [C] posts go in learning path section, [EX] in Practice Exercises, [FR] skipped | Yes |
| 6 | Run `python _build/build.py` to generate full HTML page + update sitemap/feed | No |
| 7 | Print summary (title, URL, word count, code blocks) | No |
| 8 | Stage files, commit, push to origin/master | Yes |
| 9 | (--dry-run only) Print "Dry run complete" and stop | — |

**Sidebar section mapping (Step 5):**
The skill reads `sidebar_section` from the markdown frontmatter to determine placement. Fallback: look up `curriculum_id` in `curriculum-status.json` and map the path. See `_build/frontmatter-spec.md` for the full mapping table.

**Files staged in Step 8:**
- `posts/<slug>.md` (markdown source)
- `_posts/<slug>.html` (HTML fragment)
- `<slug>.html` (built page)
- `sitemap.xml`, `feed.xml` (auto-updated by build.py)
- `www/sidebar.json` (if modified — [C] and [EX] posts only)
- NOT `curriculum-status.json` (gitignored)

### `/write-and-publish` — End-to-End Pipeline

**What it does:** Chains `/write-post-interactive` then `/publish-post` into one unattended flow.

**Input:** A topic string, optional `--dry-run`

**Output:** A live tutorial page from scratch.

**Process:**
1. **Phase 1 (Write):** Execute `/write-post-interactive` with the topic
2. **Phase 2 (Publish):** Execute `/publish-post` with the slug from Phase 1
3. **Phase 3 (Report):** Print pipeline summary (title, URL, word count, code blocks, status)

### `/auto-link` — Internal Linking Engine

**What it does:** Scans all published HTML pages and injects internal links for registered terms, plus "Further Reading" sections for core posts.

**Not a file-based skill** — invoked as `/auto-link` in conversation.

**Input:** No args (additive), `--reprocess` (rebuild from scratch), or `--cleanup <url>` (remove links to a URL)

**Underlying script:** `python _build/auto_link.py [--reprocess | --cleanup URL]`

**Three modes:**

| Mode | Command | What it does |
|------|---------|-------------|
| **Additive** (default) | `python _build/auto_link.py` | Adds new links only. Never modifies existing auto-links or FR sections. |
| **Reprocess** | `python _build/auto_link.py --reprocess` | Strips ALL auto-links and FR sections, then rebuilds everything from scratch. Use after publishing new FR posts. |
| **Cleanup** | `python _build/auto_link.py --cleanup R-Old-Post.html` | Removes all auto-links pointing to a specific URL. Use when deleting/renaming a post. |

**How it works internally:**

1. **FR Registry Scan** (runs first in all modes): Scans `_posts/*.html` for `fr_parent` frontmatter fields. Merges discovered parent→child relationships into `www/links.json`'s `further_reading` section. Only adds new entries; never removes existing ones. Updates published/not_published status by checking if the root-level HTML exists.

2. **Term Linking:** Reads `www/links.json`'s `auto_links` array. For each published entry, finds the first occurrence of each registered term in page text and wraps it in `<a class="auto-link">`. Skips terms inside code blocks, headings, existing links. Max 15 auto-links per page. Never self-links.

3. **Further Reading Injection:** For each core post listed in `links.json`'s `further_reading` section, injects a `<div id="auto-further-reading">` block with links to published FR children. In additive mode, skips pages that already have an FR section. In reprocess mode, strips and rebuilds.

**When to use each mode:**

| Scenario | Mode |
|----------|------|
| After publishing a batch of new posts | Additive (fast, safe) |
| After publishing new FR posts that need to appear on parent Core posts | **Reprocess** (rebuilds FR sections) |
| After renaming or deleting a post | Cleanup (removes stale links) |
| First time running after many posts published | Reprocess (full rebuild) |

**Key behavior:**
- Additive mode will NOT update an existing FR section with newly published FR posts — it skips pages that already have one
- Reprocess mode strips everything and rebuilds — this WILL include both old and new FR posts
- The FR registry scan always runs first, so `links.json` is always up-to-date before linking starts

## Build Toolchain Details

### `_build/build.py` — Page Generator

Generates full HTML pages from `_posts/*.html` fragments using `_build/template.html`.

```bash
python _build/build.py    # Builds all posts, updates sitemap.xml and feed.xml
```

**Template placeholders:** `{{TITLE}}`, `{{CONTENT}}`, `{{MATHJAX}}`, `{{WEBR}}`, `{{DESCRIPTION}}`, `{{KEYWORDS}}`

**What it does:**
- Reads each `_posts/*.html` file
- Extracts frontmatter (title, description, keywords, mathjax, webr)
- Injects content into template
- Conditionally includes MathJax and/or WebR scripts based on frontmatter
- Writes full page to root directory
- Updates `sitemap.xml` with new entries
- Updates `feed.xml` (RSS) with all entries

### `_build/md2html.py` — Markdown to HTML Converter

Converts markdown posts from `posts/` to HTML fragments in `_posts/`.

```bash
python _build/md2html.py posts/R-Closures.md    # Creates _posts/R-Closures.html
```

**Conversion rules:**
- `## Heading` → `<h2>` (toc.js generates sidebar TOC from h2 tags)
- `### Heading` → `<h4>` (site convention: h2 and h4, not h3)
- `` ```r `` code blocks → `<div class="webr-container">` with Run/Reset buttons
- Markdown tables → `<table class="table table-striped">`
- `> blockquote` → `<blockquote><p>...</p></blockquote>`
- `<details>` blocks (for exercise solutions) → passed through as-is
- Inline markdown (`**bold**`, `` `code` ``, `[link](url)`) → HTML equivalents
- Frontmatter fields carried through to the `_posts/` HTML frontmatter

### `_build/auto_link.py` — Auto-Linking Engine

See the `/auto-link` skill section above for full documentation.

### `www/links.json` — Link Registry

Two sections:

```json
{
  "config": { "max_links_per_page": 15, "skip_tags": [...], "skip_classes": [...] },
  "auto_links": [
    { "url": "R-Vectors.html", "title": "...", "terms": ["R vectors", "vectors in R"], "status": "published" }
  ],
  "further_reading": {
    "Functional-Programming-in-R.html": [
      { "url": "Infix-Functions-in-R.html", "title": "...", "status": "published" },
      { "url": "Tail-Call-Optimization-in-R.html", "title": "...", "status": "published" }
    ]
  }
}
```

- `auto_links`: Term→URL mappings for inline linking. Added when posts are published.
- `further_reading`: Parent→children mappings for FR sections. Auto-populated from `fr_parent` frontmatter by `auto_link.py`, plus manual entries.

### `www/sidebar.json` — Sidebar Navigation

JSON array of sections. Loaded by `toc.js` on every page.

```json
[
  { "title": "Learn R", "items": [
    { "href": "R-Vectors.html", "text": "R Vectors" },
    ...
  ]},
  { "title": "Practice Exercises", "items": [
    { "href": "R-Vectors-Exercises.html", "text": "R Vectors (12 problems)" }
  ]}
]
```

## Workflow: Publishing Posts in Batches

### Single Post (Interactive)
```
/write-and-publish "Random Forest in R"
```
This researches, writes, converts, builds, updates sidebar/curriculum, commits, pushes, and verifies — all in one command.

### Batch of Posts (Sequential)

For publishing many posts from the curriculum:

1. **Check what's next:** Read `curriculum-status.json` to find pending posts
2. **Write markdown:** Use `/write-post-interactive` or an agent to create `posts/<slug>.md` files
3. **Convert all:** `python _build/md2html.py posts/<slug>.md` for each post
4. **Update curriculum-status.json** for all posts (set status=published)
5. **Update sidebar.json** for [C] and [EX] posts
6. **Build all:** `python _build/build.py`
7. **Commit and push:** Stage all new files, commit, push
8. **Auto-link:** Run `python _build/auto_link.py` (additive) or `--reprocess` if FR posts were added
9. **Commit auto-link changes:** Stage modified HTML files + links.json, commit, push

### When to Use `--reprocess` vs Additive Auto-Link

- **Published only Core [C] posts?** Additive mode is fine — new terms get linked, no FR sections needed.
- **Published FR posts that should appear on parent Core posts?** Use `--reprocess` — additive mode won't update existing FR sections.
- **First run after a big batch?** Use `--reprocess` to get a clean, complete link graph.

The canonical frontmatter specification lives in **`_build/frontmatter-spec.md`** — the single source of truth for all field definitions, required-by-type rules, auto_link_terms guidance, and sidebar section mapping. All skills and commands reference that file.

Quick summary of post types and sidebar rules:

| Type | Code | Sidebar? | Key frontmatter |
|------|------|----------|----------------|
| Core | C | Yes — `sidebar_section` | `sidebar_section`, `sidebar_title`, `sidebar_order` |
| Further Reading | FR | No | `fr_parent` |
| Exercise | EX | Yes — Practice Exercises | `sidebar_title`, `fr_parent` |
| Programmatic SEO | PSEO | No | `fr_parent` |

## When Publishing a New Post (Manual Checklist)

1. **Look up the post in the curriculum** to determine its type ([C]/[FR]/[EX]) and path
2. **If [C] (Core)**: Add to `www/sidebar.json` under the correct learning path section
3. **If [EX] (Exercise)**: Add to `www/sidebar.json` under "Practice Exercises"
4. **If [FR] (Further Reading)**: Do NOT add to sidebar. Ensure `fr_parent` is set in frontmatter — auto-link will handle the rest.
5. **Update `curriculum-status.json`** with published metadata (status, slug, url, date, in_sidebar)
6. **Add breadcrumb** above the H1: `<nav class="breadcrumb-nav">Home > Learn R > Section > Post Title</nav>`
7. **Add featured snippet subtitle**: A `<p class="lead">` definition paragraph after the H1

## Code Style in Tutorials

- Use `<-` for assignment (R convention), not `=`
- Show output as `#>` comments in code blocks
- Include `library()` calls in the first code block
- Use built-in R datasets (mtcars, iris, airquality) or generate sample data inline
- Keep each code block focused on ONE concept (5-25 lines)
- Code blocks share state across a page (WebR session persists like Jupyter cells)

## URL Structure

- All posts live at root level: `r-statistics.co/<slug>.html`
- Slug derived from title: `R-Data-Types.html`, `Functional-Programming-in-R.html`
- File naming convention: `Title-With-Dashes-And-Capitals.html`

## Git Workflow

- Push directly to `master` branch (GitHub Pages deploys from master)
- No branch protection or PR workflow
- Do NOT commit `curriculum-status.json` (gitignored)
- Do NOT include `Co-Authored-By` lines in commit messages
